# task-capability · decisions

### [2026-11-03] 终态形态分岔采用「公共内核 + 形态分支」结构，跨 App 任务形态待裁决 (src: ai 评估 + 用户提问驱动)
- **场景/痛点**：终态诉求含四项——配合其他 App 处理单次任务、调用其他 App 的工具操作其 App 内数据、用云端模型并配合云端处理涉及隐私的杂活、云端能力轻量化在本地实现。四项诉求落在两个互斥的终态形态上：goodhub 作为 **Worker**（消费各 App 任务队列，任务本体留在来源侧）或作为**编排者**（持有跨 App 任务本体并调度参与方）。两者的落地量差约四倍，且 (B) 与来源 App 的任务事实源形成双持，须在跨仓接缝上明确归属划分。未裁决前若直接建 (B) 的任务实体，返工面覆盖整个任务层。
- **可选方案（含否决理由）**：
  - 单一终态直写设计稿（**否决**：终态形态未裁决时写死任一形态，另一形态的全部工作要么作废要么重做）；
  - 公共内核 + 形态分支（**采纳**）：能力需求声明、供给面契约、路由判据链、开放边界在两形态下完全共用，差异仅在跨 App 接入段（形态 A = 多来源队列适配 + 对账分组；形态 B = 任务实体 + 生命周期 + 作用域 + 跨 App 取消/进度/失败域/并发仲裁）。裁决结果只裁掉分支段，公共内核不返工。
  - 隐私分级纳入本轮设计（**否决**：用户 2026-11-03 明示「先不考虑隐私，现在考虑隐私太早了」）。
- **最终决定**：① 终态形态分岔采用公共内核 + 形态分支结构，落 `docs/design/on-device-task-capability.md`（draft）；② 形态 A / B 记为待裁决决策项 D1，gate 跨 App 接入段全部工作包；③ 端侧原语边界记为待裁决决策项 D2，gate 供给面收口段全部工作包；④ 隐私分级、遮蔽前移、端侧 redact 原语整体推后，登记为待复评议题，不在本 epic 施工。
- **AI 洞察**：终态设计的未裁决部分集中在**产品定位**层（goodhub 是执行方还是编排方），而非工程层；把裁决点显式隔离到接入段后，工程侧可立即开工的比例从「等全部裁决」提升到「内核全开 + 分支等裁」。另一条洞察：隐私设计的必要性依赖终态形态——形态 A 下数据流单向，来源层打标不存在；形态 B 下才需要。**在形态未定前做隐私层改造等于赌一个还没定的终态**。
- **收敛条件**：D1/D2 由产品与架构拍板后，同轮回写本文件与设计稿 §8，解除对应工作包的 gate；形态 B 立项时须同轮修 goodshare 仓 `docs/design/ai-app-split.md` 明确任务事实源归属。

> 本条的两项待裁决项已由同日的「终态形态四项裁决」ADR 落定（D1 = 形态 A、D2 = a），本条的其余结论（公共内核 + 形态分支结构、隐私线推后）继续有效。

### [2026-11-03] 路由判据从隐式推断改为显式能力需求声明 (src: ai 评估)
- **场景/痛点**：现行路由判据是两个间接信号——请求是否携带工具（`hybrid_cloud_engine.dart`）、工具面是否全为宿主本地元工具（`hybrid_assembly.dart`）。二者把「要动别人的数据」「要调工具」「任务复杂度」「端侧是否适用」压在同一个布尔判断上，导致：端侧适用性不可测；新增供给面（新的端侧后端、新的外部工具源）必须改路由逻辑；判据优先级散落多处（偏好 / 准入画像 / 降级冷却 / 工具面）无单一顺序。
- **可选方案（含否决理由）**：
  - 扩展 `CloudChatRequest` 增加能力需求字段（**否决**：该结构是引擎无关的云请求契约，端侧适用性需求写入会污染它，且 `ToolRouter` / `AgentLoop` 也需读该声明，挂在云请求上位置错置）；
  - 独立值对象 `CapabilityRequirement`（**采纳**）：任务或步骤级声明「需要什么」而非「看起来像什么」；
  - 维持现状靠加判据（**否决**：命中 solution-admission 信号 #2——同一处理在第二、第三调用点重复写；且判据不可测）。
- **最终决定**：① 引入 `CapabilityRequirement` 值对象（维度：需工具 / 需结构化产出 / 可离线 / 数据体量档 / 偏好本地）；② 缺省一律取保守侧（宁可选云端，不误判端侧可用），缺省行为本身是被测对象，新增维度须显式给缺省值 + 同步回归钉；③ 路由优先级固定为 **声明 > 用户偏好 > 准入画像 > 降级链冷却态**，声明优先于偏好，使「声明不可满足」显式失败而非被偏好覆盖；④ 判据链落空原因逐级可区分，不合并为单一「端侧不可用」；⑤ 端侧适用性的事实基础落一张对照表（任务类型 × 可行性），数据源为既有真机基准与 `on_device_bench.dart`，表结构在 `assets/model-specs.json` 的 bundle 条目上扩展。
- **AI 洞察**：判据从推断改为声明后，端侧适用性第一次成为**可回归的对象**——这比「多一条判据」的价值大得多：它使端侧投入决策从拍脑袋转为有据可查，也为新增供给面留出不改路由的扩展面。附带效应：对照表成为后续端侧能力建设的决策基础设施，其价值独立于本设计。
- **收敛条件**：声明维度每次新增须同轮补缺省值回归钉；对照表数据随端侧模型或引擎栈变更时同轮刷新，格式与既有基准归档保持一致。

### [2026-11-03] 供给面契约与语义外注边界，隐私线整体推后 (src: 用户拍板 + ai 评估)
- **场景/痛点**：诉求含「云端能力轻量化在本地的实现」，其落点有两条：一是端侧提供与云端同形的无状态完成能力（本地替身），二是端侧内置具体任务语义（摘要/打标签/分类的实现）。既有 ADR（on-device epic 待裁决项「能力原语化 + 跨 App 转发」）明写端侧只提供模型能力原语 `complete(instruction,input,config)`、**不含任务模板**，任务语义由其他 MCP 服务编排实现——与诉求第二条方向相反。同时隐私相关议题（敏感度分级、遮蔽前移到来源层、端侧 redact 原语）在本轮被提出，但端侧模型质量前提尚未成立（长指令复读环严重为已接受的已知限制），非结构化 PII 的端侧遮蔽质量不可靠。
- **可选方案（含否决理由）**：
  - 端侧内置具名原语族（摘要/分类/提取/改写）（**否决**：违反既有 ADR 的边界——把任务语义搬回客户端；且与「跨 App 转发端侧算力」目标相悖，转发方需要的是通用能力而非固定语义）；
  - 供给面只提供无状态完成能力 + 任务语义由外部注入（**采纳**，语义注入复用既有 `SkillRegistry` 与 CoW 同步机制，不新造注入通道）；
  - 本轮同时设计隐私分级（**否决**：用户明示推后；且必要性依赖终态形态——形态 A 下数据流单向，来源层打标不存在，形态 B 下才需要）。
- **最终决定**：① 供给面三项结构性约束：无状态（跨调用不复用隐式上下文，可复用部分由调用方显式携带）、任务语义外注（`instruction` 参数或 Skill 体系，端侧不内置任务模板中心）、结构化保证（失败类型化 + 留痕 + 可行动原因，降级路径同受约束）；② 语义注入通道复用 `SkillRegistry` 与 CoW 同步机制（`cow/<promptName>` 命名注册、撞名跳过并通告），不新造注入机制；③ 隐私分级、遮蔽前移、端侧 redact 原语整体推后，登记为待复评议题（触发条件：隐私线启动 / 端侧模型质量实证）；④ 既有 ADR 的边界维持不变，语义外注路线与其一致。
- **AI 洞察**：供给面与任务语义解耦后，端侧成为**可被任意编排方调用的算力**，这恰好是「配合其他 App 处理单次任务」所需的形态——协作方需要的是能力，不是端侧替它决定做什么任务。另一条：在模型质量未证实的阶段把语义内置进端侧，会把「模型不行」与「架构不行」两种失败混在一起，无法归因。
- **收敛条件**：若后续出现「端侧必须自带某类语义才能被调用方接受」的实证需求（如跨 App 转发的协议要求固定语义），则重开 ADR 修订本条，届时须同时评估语义维护面归属；端侧模型质量实证后重评 D14（端侧 redact 原语）。

### [2026-11-03] 工程选型八项定案 (src: ai 评估)
- **场景/痛点**：终态落码前有一批形态级工程选型待定（声明载体、对照表落点、主体身份形态、常量收纳、语义注入通道、导出面命名、多来源接入协议、会话切分粒度）。这些不属于产品定位裁决范围，等待只会拖慢可开工部分。
- **最终决定**：D3 能力需求声明载体 = 独立值对象，不改 `CloudChatRequest`；D4 端侧适用性对照表落点 = `assets/model-specs.json` 的 bundle 条目扩展（加载器现成）；D5 主体 App 身份 = 包名 + 签名指纹双字段（与插件信任判据同源）；D6 端侧常量收纳 = drift-registry `CONST` 登记，不建端侧专属常量件（机制现成，建新件等于造第二套）；D7 语义注入 = 复用 `SkillRegistry` 与 CoW 体系；D8 端侧能力导出面 = `host__` 命名空间扩项，不新建命名空间（Allowlist 与保留字断言已成型）；D9 多来源接入协议 = 保留各 App 私有任务工具 + goodhub 侧泛化适配（各 App 任务语义不同，统一协议属过度设计）；D10 会话切分粒度 = 一件可独立验证的改动 = 1 会话，跨端不拆包，真机验证单独计人工场次。
- **AI 洞察**：八项里六项的答案是「复用现成机制」而非新建——这轮选型的最大价值不是决策本身，是**确认了终态大部分构件在本仓已有载体**（Skill 体系 / Allowlist 导出面 / drift-registry / model-specs 加载器 / bundle 对账），终态的落地成本因此低于直觉。D5 与既有插件信任判据同源是刻意选择：跨 App 主体身份若与信任身份不同源，会出现「信任认得它、授权认不出它」的割裂。
- **收敛条件**：任一选型在开工时发现现成机制不适用（如 `SkillRegistry` 无法承载端侧语义注入、`model-specs.json` 结构不足以承载任务亲和性），按 solution-admission 重新判定，不得以「已经定了」为由硬塞——选型定案不等于免评估。

### [2026-11-03] 外部评审采纳：执行槽主体分类 / 冷热态 / token 预算 / 调用方配额 (src: 外部评审 + ai 实证复核)
- **场景/痛点**：设计稿出稿后经外部评审，提出四处补强——① 端侧并发与生命周期竞争（执行槽抢占与互斥纪律）② 上下文窗口与 token 预算声明的可度量性 ③ 跨 App 调用算力的认证与配额攻击防范 ④ 路由判定链的时延与冷启动惩罚。经代码实证复核：评审四条中两条的「现状盲区」描述与代码不符（单执行槽的策略 B 与前台抢占已落地；端侧超窗预检与拒绝切云已定稿），但四条指向的缺口部分成立——缺口不在机制层，在**声明层与开放面**。
- **可选方案（含否决理由）**：
  - 全盘采纳并新建机制（**否决**：评审原文有「另建 Token Bucket / Rate Limiter」倾向，照做会在仓内造出第二套执行槽、第二套限流器、第二套 token 估算，违反单源纪律）；
  - 按缺口性质分流——机制层已有者复用并扩展主体分类，声明层缺者补维度，开放面缺者补配额（**采纳**）；
  - 维持原稿（**否决**：声明层缺时效与 token 预算维度，开放面缺资源治理，而开放终态引入的是新暴露面）。
- **最终决定**：① 供给面约束由三项扩为五项，新增「执行槽主体分类」（交互级可抢占；后台与外部调用遇槽占用即驳回转云端、不排队；跨 App 场景主体属性以调用方为准而非宿主）与「冷热态区分」（交互级遇冷态不静默等待装载；装载触发权归调用方，供给面调用本身不触发装载）；② 能力需求声明新增两维——`tokenBudget`（可度量值，估算复用 `lib/core/tokens.dart` 口径，窗口准入判定复用既有超窗预检纯函数与上下文超窗异常，端侧路径不另写第二套截断或估算）与 `latencyClass`（交互级／批处理级，缺省批处理级）；③ 路由判定链扩为六段（声明 → 窗口准入 → 时效 → 端侧就绪 → 准入画像 → 云端可达），前两段属声明自身可满足性、后两段属端侧当前状态，分开使「声明不可满足」与「端侧暂不可用」在用户文案与降级路径上不混淆；④ 开放边界新增按调用方身份的速率配额与并发上限（配额形态复用既有反向请求配额池，不新建限流器），且后台调用方的冷装载请求不被自动满足；⑤ 形态 B 的协作难点改按工程约束表述（取消传播 / 部分失败 / 事实源双持），不引入分布式事务框架——形态 B 是普通跨进程 RPC 编排，不涉两阶段提交，按事务框架设计会过度工程化；⑥ 新增待裁决 D3（交互级遇冷态处置）与 D4（语义外注后宿主自身提取分类消费如何处置）。
- **AI 洞察**：评审最有价值的贡献不是它指出的缺口，而是**它把「端侧算力作为可被外部调用的系统级资源」这件事的性质点了出来**——算力与普通工具调用不同，耗电发热内存三重密集且共享单执行槽，把它开放出去即引入攻击面；原稿把开放边界写成了「导出形式」，漏了「资源治理」。另一条：评审的两处误判暴露了一个流程事实——**文档评审若不伴随代码取证，会把既有机制当缺失**，据此提出的「新建」建议会直接违反单源纪律；故本轮处置是每条评审意见先落代码实证再判采纳。另修正一处编号冲突：终态裁决、工程选型、推后隐私议题三类决策项此前共用 D 前缀，改为 D／E／P 三类分编，跨文件引用带类前缀。
- **收敛条件**：D3 裁决前，W2 的时效判定按最保守档（显式分流云端）实现，随裁决调整但不阻塞 W2 其余部分；D4 未裁决则 W3 不开工，避免「有供给无消费」；配额与执行槽的复用性在 W5 开工时按 solution-admission 复核——若既有机制确不适用才允许新建，且须同轮登记为单源常量或超标件。

### [2026-11-03] 终态形态四项裁决：Worker / 通用原语 / 冷热态分级 / 语义注入迁移 (src: 外部评审第二轮 + ai 实证复核)
- **场景/痛点**：设计稿经两轮外部评审后，四项终态形态决策具备裁决条件。第二轮评审给出四项裁决建议（形态 A、通用原语、冷热态分级策略、语义注入路径的「自产自销」破局），另提出两处边界钉（同机通道调用方身份取证、外部调用触发的内存水位门槛）。逐条代码取证复核后发现三处须修正：① 评审的「形态 B = 分布式事务难题」框架误用——形态 B 是普通跨进程 RPC 编排，真实难点是取消传播、部分失败语义与事实源双持，按事务框架设计会过度工程化；② 评审建议的内存门槛数值 400MB 低于现有全部水位线（起跑 1.2GB / 棘轮 1.6GB / 硬失败 0.9GB / 绝对地板 1GB）且无实测依据；③ 评审的语义注入破局方案存在硬前提缺口——端侧生成参数契约当前无约束解码规格（约束解码真机实证来自旧裸机桥路径，引擎换线到独立进程通道后未被承载），迁移到语义注入路径若无约束解码承载，Skill 化的分类无输出格式保证，等于能力降级。
- **可选方案（含否决理由）**：
  - 形态 B 并行推进（**否决**：落地量约四倍，且与来源 App 任务事实源双持，跨仓接缝须谈归属；当前无多 App 双向穿梭的强业务诉求）；
  - 形态 B「封存至下个大版本」（**否决**：无判据的封存会长期挂起如 G1，须写成带触发条件的解封门禁）；
  - 供给面内置任务模板（**否决**：端侧资产与宿主业务代码耦合发版，与资产独立分发现状冲突；且使端侧成为任务语义中心，与跨 App 转发端侧算力的目标相悖）；
  - 交互级遇冷态统一分流云端（**否决**：网络不可达时分流必然失败，且「可离线」类任务本以端侧为唯一路径，统一分流会把唯一可完成路径判死）；

### [2026-11-03] 现实运行尺度评审采纳：治理违规不切云 / 排除位 / 协作打断 / 前缀留位 / 门禁四类 (src: 外部评审第三轮 + ai 实证复核)
- **场景/痛点**：评审以「上线 3~6 个月后接入真实业务与外部 App」的时间尺度，指出四处内在张力：① 准入落空一律分流云端，使配额超限也走云端，等于外部调用方高频滥用时由宿主承担暴涨的云端账单与并发压力，配额形同虚设；② 无状态原语与端侧预填充成本冲突（长上下文预填充为秒量级，逐次调用重算不变前缀放大时延与能耗），且宿主提取分类迁入该路径后会连续触发；③ 槽位「抢占」在物理层不可实现（底层算子阻塞不可切分，中断只在生成循环检查点生效），等待窗口耗尽后无解；④ 算力导出若沿用普通工具的门禁路径，会绕过速率与资源额度维度。逐条代码取证复核：②③ 与仓内既有登记逐字对应（前缀侧 `GenieSession.query` 每请求 `runBlocking { w.reset() }`，与前缀复用声称的矛盾已登记为待实证项；打断侧既有登记「抢占等待可能被停止流调用吃掉、绝不驳回用户实际降级为绝不立刻满足、响应性未实证」），故两处批评的事实基础完全成立；①④ 的方向成立但④ 的具体后果需修正。

  - 配额超限改为快速失败并给类型化异常（**采纳**）；

  - 把前缀复用做成供给面的新缓存机制（**否决**：既有前缀缓存与上下文回滚能力已存在，供给面新造机制等于造第二套；改为契约暴露既有能力）；
  - 在契约中承诺前缀复用命中率（**否决**：该前提未实证，承诺即失信；改为契约先留位、收益待实证）；
  - 继续称「抢占」并承诺前台绝不驳回（**否决**：物理层不成立；改为协作式打断的准确表述与耗尽处置）；
  - 为算力新建独立命名空间与专用协议（**否决**：代价是第二套导出面、第二套保留字断言、第二套投影策略适配，与既有工程选型冲突；导出面的分派判定本就是通用规则、不携带条目治理语义，故「dispatcher 臃肿」不成立）；
  - 在导出面引入第四类门禁（资源治理）并与权限门禁正交（**采纳**）。
- **最终决定**：① 准入落空分两类——资源故障（窗口不足 / 时效不可接受 / 端侧未就绪 / 后端被排除 / 内存低于地板）分流云端保产出，治理违规（配额超限）快速失败并抛类型化异常，不切云；内存地板落空仍分流云端，因云端不在本机执行、本机内存紧张不影响云端产出，快速失败等于把唯一能产出的一侧判死；② 能力需求声明增排除位（显式禁止云端，落空时快速失败），与下限约束（云端不可达时仍须可完成）正交；③ 打断表述从抢占改为协作式打断——底层算子阻塞不可切分、中断只在生成循环检查点生效、等待窗口耗尽不得假设打断已生效，须按策略性降级处置（切云或显式上浮等待），不得以重启引擎腾算力（重启即冷装载，代价为秒级装载与前台卡顿）；④ 供给面契约增可选前缀复用句柄，引用既有前缀缓存与上下文回滚能力，句柄由供给面返回、调用方显式持有与失效，收益未实证前不承诺命中率；⑤ 导出面门禁拆为四类（可见性 / 权限 / 标注 / 资源治理），前三类适用全部导出条目，第四类只对资源消耗型条目生效，算力导出项须逐类通过；不新造命名空间。
- **AI 洞察**：本轮四条批评的共同根因是**把「产出优先」当成无条件的最高原则**——但产出优先只在「故障」域成立，在「治理」域不成立：把违规请求转到云端，是用宿主的账单与容量替违规方买单，等于把安全机制反转为攻击通道。第二条根因是**把物理约束写成了能力承诺**：「可抢占」与「响应性未实证」这两件事在仓内同时成立，说明设计稿的措辞跑在了实现证据前面；修正方向不是改实现去追承诺，而是把措辞降到证据允许的范围内——这比补一个缓存句柄更重要，因为它同时消除了「前台绝不驳回」这类无法兑现的用户承诺。第三条：评审对导出面的具体后果判断有误但方向正确，说明「分层」讨论里机制位置比机制数量更重要——门禁四类中前三类回答「能不能调」、第四类回答「调得起吗」，把第四类塞进只覆盖前三类的通道，等于让治理维度整体缺位。
- **收敛条件**：配额超限的类型化异常须可被调用方区分（配额语义与引擎故障语义分离），验收钉覆盖「配额耗尽 → 不产生云端调用」；前缀复用句柄本期只落契约与句柄传递，命中率承诺待端侧前缀缓存实证结论回填后另行评估；协作打断的等待窗口耗尽路径须有回归钉（前台请求在打断失败时走切云而非超时）；导出面第四类门禁在开放期随算力导出项一并落地，落地前算力不得对外暴露。
